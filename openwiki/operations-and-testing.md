# Operations & Testing

## Build / test / publish

This is a standalone npm package (`tennisjs`), ESM (`"type": "module"` in
[`package.json`](../package.json)), compiled with `tsc` per [`tsconfig.json`](../tsconfig.json)
(`target: ES2015`, `module`/`moduleResolution: NodeNext`, `strict: true`, declarations emitted).

| Command | What it does |
|---|---|
| `npm run build` | Runs `tsc`, compiling `src/**/*` to `dist/` (with `.d.ts` declarations). |
| `npm test` | Runs `jest` against everything in `tests/`. |
| `npm publish` | Triggers `prepublishOnly` → `npm run build` first, then publishes `dist/` (per `package.json` `"files": ["dist"]`) plus `package.json`/README/LICENSE to npm as `tennisjs`. |

Jest is configured in [`jest.config.cjs`](../jest.config.cjs) with the `ts-jest/presets/default-esm`
preset (`testEnvironment: "node"`), a `moduleNameMapper` that strips `.js` extensions from
relative imports (needed because source uses NodeNext-style `.js`-suffixed imports even though
the files are `.ts`), and `ts-jest` configured with `useESM: true`. If you add a new test file or
hit ESM-related import errors, check this config first — it's the reason all internal imports in
`src/` use `./foo.js` rather than `./foo.ts`.

There is no linter or formatter script wired into `package.json` beyond a `prettier` devDependency
— there's no `npm run format`/`lint` command; formatting is manual/editor-integration only as far
as this repo's tooling goes.

## Test file map

All tests live in [`tests/`](../tests) and import from `../src` (the package root, exercising the
same surface a consumer would via `src/index.ts`).

| File | What it protects |
|---|---|
| [`match1.test.ts`](../tests/match1.test.ts) | Core singles scoring: point→game conversion (0/15/30/40, deuce, advantage), server tracking, `removePoint()` undo at the point level, using a shared running `match` instance and a `scoreAndTest` helper that asserts the full `[sets, games, points]` tuple after each point. |
| [`match2.test.ts`](../tests/match2.test.ts) | Full-match completion and undo/redo **at match/set boundaries** (winning full sets, checking `winner`/`status` fields, undoing across a completed set boundary). |
| [`doubles.test.ts`](../tests/doubles.test.ts) | Doubles team structure (`type: "team"`, two `TeamPlayer`s), serving-rotation initialization and order (`T1A → T2A → T1B → T2B`), rotation continuing correctly across games. |
| [`unified-match.test.ts`](../tests/unified-match.test.ts) | End-to-end `UnifiedMatchSummary` shape for both singles and doubles: deuce/tiebreak/set/match completion, `matchScore` string formatting, basic per-point stats sanity checks, `removePoint()` at the point level. |
| [`statistics-collection.test.ts`](../tests/statistics-collection.test.ts) | Detailed singles + doubles statistics correctness per `PointOutcome` (ace, double fault, service winner on 1st/2nd serve, regular points) — the low-level companion to `docs/statistics.md`. |
| [`augmented-stats.test.ts`](../tests/augmented-stats.test.ts) | Doubles **individual player attribution** exclusivity — e.g. asserts that only the scoring player's `playerStats` entry gets credit for a winner, not teammates or opponents. Added alongside the `5e46a21` "improve unforced error collection" stats fix. |

When changing scoring rules, run the whole suite (`npm test`) — `match1`/`match2`/`unified-match`
all assert exact score tuples after sequences of points, so a scoring-math change that's correct
for one format (e.g. tiebreak) can silently break another (e.g. deuce) if not tested broadly.
When changing statistics logic, `statistics-collection.test.ts` and `augmented-stats.test.ts` are
the primary guard rails — update [`docs/statistics.md`](../docs/statistics.md) in the same change
so the reference doc doesn't drift from behavior.

## CI: this repo's own OpenWiki loop

[`.github/workflows/openwiki-update.yml`](../.github/workflows/openwiki-update.yml) runs on a
daily cron (`0 8 * * *`) and on manual dispatch. It installs the `openwiki` CLI globally, runs
`openwiki code --update --print` against this repository, and opens a PR (via
`peter-evans/create-pull-request`) on branch `openwiki/update` containing any changes under
`openwiki/`, `AGENTS.md`, `CLAUDE.md`, and the workflow file itself. In other words: **this
repository is itself an OpenWiki consumer** — the wiki you're reading is expected to be
periodically regenerated by that workflow, not hand-maintained. Don't be surprised to see
`docs: update OpenWiki` PRs in the repo's history; they are automated, not manual edits.

There is no other CI (no separate lint/test workflow file exists at the time of writing) — running
`npm test` locally before pushing is the main correctness gate.

## Historical / superseded documentation

Three root-level markdown files predate the v3.0 refactor and describe a data model that was
later deleted:

- [`implementation-next-steps.md`](../implementation-next-steps.md)
- [`unified-data-model-design.md`](../unified-data-model-design.md)
- [`unified-model-implementation-summary.md`](../unified-model-implementation-summary.md)

They describe the intermediate "unified API running alongside legacy classes" design (commit
`0563c5e`), which was superseded when `7ac7103` ("Major refactoring — not backwards compatible")
deleted `Game.ts`, `Point.ts`, `Set.ts`, `TieBreak.ts`, `LegacyTennisMatch.ts`,
`legacy-adapter.ts`, and `unified-types.ts`. **Do not use these three files as a guide to current
architecture** — see [Architecture](architecture.md) for the current, accurate module map and the
full history of how the codebase got here. They're left in the repo as historical record of
design intent, not as documentation to trust for current behavior.

## Extension points & watch-outs for future changes

- **New `PointOutcome`**: add to the enum in `src/types.ts`, wire it into `updateStats()` in
  `statistics-aggregator.ts` (serving/returning/rally switch statements), update
  `docs/statistics.md`, and add a case to `statistics-collection.test.ts`.
- **New public API**: implement in the relevant module, then re-export from `src/index.ts` — this
  file is the entire contract; anything not exported here is effectively private even if it's a
  top-level export in its own module.
- **Scoring rule changes** (no-ad scoring, short sets, custom tiebreak points): `MatchFormat` in
  `types.ts` already has `noAdScoring?`/`shortSets?` fields defined, but `TennisMatch.ts`'s
  private scoring methods (`convertToTennisScore`, `checkGameWinner`, `checkSetWinner`) do **not**
  currently branch on them — they're reserved/unimplemented fields, not active toggles. Confirm
  this by grepping the field name in `TennisMatch.ts` before assuming the feature works.
  the same "reserved but unwired" pattern shows up in several `ParticipantStatistics` fields (see
  [Domain & Workflows](domain-and-workflows.md#statistics-model-overview) and
  `docs/statistics.md`) — always check whether a field is actually read/written before trusting a
  type definition's presence as a behavior guarantee.
- **Statistics undo**: if you fix the "stats not rolled back on undo" limitation (see
  [Domain & Workflows](domain-and-workflows.md#undo-semantics-removepoint)), you'll need a
  `StatisticsManager.removePoint()`-equivalent and to un-flag the TODO comment in
  `TennisMatch.ts` — this is the most likely "known gap" a future contributor will be asked to
  close.
- **Serialization changes**: `toJSON()`/`fromJSON()`/`SerializedMatch` (in `types.ts`) must stay
  in sync with any new private field added to `TennisMatch` — forgetting to add a field to all
  three places silently breaks save/resume without a compile error (since `fromJSON` assigns
  fields individually rather than via a single typed constructor call).
